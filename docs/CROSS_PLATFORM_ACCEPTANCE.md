# macOS and Windows acceptance checklist

Use this checklist on clean copies of the same source tree before the first
GitHub release. Do not copy an existing `.venv` between computers.

For the prepared 1.0.3 candidate, start at `START_HERE.md` and use the supplied
synthetic example. Scripted checks already performed during preparation are
recorded separately in `RELEASE_READINESS.md`; they do not fill in your manual
laptop checks below.

## Test layout

Create a dedicated folder on each computer:

```text
rna_mod_workspace/
├── rna_mod_pipeline/     # clean copy of this repository
├── data/                 # external references and databases
├── rna_mod_demo/          # synthetic example, generated by test_demo_*
└── refactored_outputs/   # created by the GUI and commands
```

The double-click launchers intentionally use `rna_mod_workspace/` as the
project workspace. This keeps large inputs and generated results outside the
Git repository.

Use a workspace path containing a space on at least one computer, such as
`RNA mod test`, to exercise path handling.

## Installation and launch

### macOS

1. Confirm that no `.venv` exists in `rna_mod_pipeline/`.
2. Double-click `install_macos.command` and require a successful completion.
3. Double-click `run_macos.command` and require the GUI to open without a
   traceback.
4. From Terminal in the repository root, run the regression suite:

```bash
.venv/bin/python -m unittest discover -s tests -v
```

If macOS removed executable permissions during file transfer, run this once
from the repository root:

```bash
chmod +x *.command
```

### Windows

1. Confirm that no `.venv` exists in `rna_mod_pipeline\`.
2. Double-click `install_windows.bat` and require a successful completion.
3. Double-click `run_windows.bat` and require the GUI to open without a
   traceback.
4. From Command Prompt in the repository root, run the regression suite:

```bat
.venv\Scripts\python.exe -m unittest discover -s tests -v
```

## Resource validation

### Self-contained first trial

After installation, double-click `test_demo_macos.command` or
`test_demo_windows.bat`. This runs the regression suite, prepares a new sibling
`rna_mod_demo/` workspace, executes the synthetic Phase 1, three-database loose
and transcript-region analyses and cross-database comparisons, then checks the
known answers. It refuses an existing nonempty demo workspace.

Expected core counts are 800 raw rows, 384 filtered cases, 384 eligible
controls, 288 DRACH-positive cases, 32 genes and 96 transcript-region strata.
The artificial `DEMO_ENRICHED` and `DEMO_DEPLETED` tracks have expected odds
ratios 9 and 1/9 in every database and both overlap designs. The other sentinel
tracks cover neutral, zero, infinite and non-estimable cases. These numbers
are test definitions, not project results.

Open `run_demo_macos.command` or `run_demo_windows.bat` to inspect the generated
workspace. The Resources and dataset profiles are already configured for
synthetic inputs. Follow `examples/acceptance/README.md` for the exact result
paths and an independent verification command. In Results, select the relevant
output folder or enter its manifest path and choose **Load manifest**.

### Real-resource second trial

In **Projects and datasets → Resources…**, configure the resources needed for
the workflows being tested. At minimum for the test below, configure:

- hg38 reference FASTA and its adjacent `.fai`;
- GENCODE v44 GTF;
- bundled `rna_mod_pipeline/config/rbp_catalog.tsv`;
- one binding resource, preferably oRNAment for the compact cross-platform
  comparison.

Run **Check resources…**. From a terminal opened in `rna_mod_pipeline/`, also
run:

```bash
.venv/bin/rna-mod-doctor --project-root ..
```

On Windows Command Prompt, use:

```bat
.venv\Scripts\rna-mod-doctor.exe --project-root ..
```

Use `--full` only when every optional expression, KnockRBP, ENCORI, and POSTAR3
resource is present. Otherwise require only the resources needed for the
selected test; an unavailable optional resource is not a failed installation.

## Functional acceptance

Use the supplied synthetic input on both computers first. For the second trial,
use the same experimental input and verified reference/resource snapshots.

1. Register the bedMethyl as a new named dataset.
2. Run **Phase 1 · Filter bedMethyl**.
3. For m6A, run **Phase 1 · DRACH annotation**.
4. Run **Phase 1 · Transcript annotation**.
5. Run one oRNAment loose-overlap analysis.
6. Run one oRNAment transcript-region analysis.
7. Open the result tables and at least one PNG from the Results screen.
8. Close and reopen the GUI; confirm that the resource profile and datasets
   reload. Reload a completed manifest from Results and confirm the outputs
   still open. Logs from GUI-launched jobs remain on disk; an automatic job-
   history browser is not part of this version.
9. Start a disposable run, cancel it, and confirm that an earlier completed
   output remains intact.
10. Confirm that results were written below
    `rna_mod_workspace/refactored_outputs/`, not inside the repository.

ENCORI, POSTAR3, KnockRBP, and online STRING runs are additional full-resource
acceptance tests. They are not required to prove that the installer and GUI are
portable, but each should be tested before its workflow is relied on for a new
production analysis.

The synthetic demo already exercises each binding adapter, but it does not
replace checking real database format/content or actual internet access for
STRING. The portable doctor is a structural check, not a complete scan of
every biological record.

## Cross-platform comparison

Compare the macOS and Windows TSV outputs produced from identical inputs and
parameters. Row identities, statistical values, classifications, and manifests'
scientific parameters should agree. Compare numeric columns with a small
floating-point tolerance if text serialisation differs.

Keep each demo's `acceptance_check.json` and source version/checksum. Both
must pass their independent expected-answer checks. Native platform/version
information and paths may differ. Raw snapshot hashes are appropriate only
for input files generated identically on both computers.

Do not require PNG files to have identical hashes. Fonts and rendering can
differ by operating system even when the plotted data are identical; compare
their source-data TSVs and inspect the images instead.

## Cleanliness and reset

After recording the results:

1. Run the platform's `reset_environment_*` helper.
2. Confirm that only the local `.venv` was removed.
3. Confirm that external data and `refactored_outputs/` remain intact.
4. Confirm that the repository copy contains no raw data, result folders,
   credentials, logs, build artefacts, or machine-specific absolute paths.
